# Evidence: keel-host-keys generates its independent keys in parallel, 2026-10-27

Change: `bin/keel-host-keys` runs each `ssh_key` type, `tls_pair` and
`snakeoil_pair` in a subshell at once, then waits; a failing subshell
sets the unit's exit status. The functions write different files, read
the same shared-key list, and keep their own `umask 077`.

Measured on the Core layer's first boot before the change:

```text
1.152s keel-host-keys.service
```

The three SSH keys, the TLS pair and the snakeoil pair are independent;
the parallel run is bounded by the slowest generator, not their sum.
`tests/test-host-keys.bats` passes 22/22, including the failure cases
(ssh-keygen, turnkey-make-ssl-cert, make-ssl-cert and the missing
shared-key list). The next Core boot measures the service and
`systemd-analyze blame`.

## Image before the local build

The Core image shipped the apt inithooks; its first boot measured
**1.327 s** for `keel-host-keys.service`. The parallel 2.3.6+keel27
build is not in that image yet; the next image build installs the local
`.deb` after the plan and measures the same service.

## RNG re-measure, 2026-10-28

With `-smp 4` and `-device virtio-rng-pci`, the image with the local
2.3.6+keel27 measured **1.066 s** for `keel-host-keys.service` on the
first boot. The apt sequential build measured 1.327 s, and the earlier
2-vCPU/no-RNG run measured 1.719 s. The parallel build is a real but
modest win; the 1.719 s was the test VM's missing entropy, not the code.
`tests/test-host-keys.bats` passes 22/22.

## First boot with the boot layer, 2026-10-28

`keel-host-keys` measured **939 ms** on the first boot of the Core image
with the 6.12.113 boot layer, 4 vCPUs and virtio-rng. The apt sequential
build was 1327 ms; `turnkey-init-fence` added 256 ms on the first-boot
path. The 939 ms is the best of the three runs and confirms the parallel
build; the earlier 1719 ms was entropy-bound.

## Final first boot, 2026-10-28

`keel-host-keys` 935 ms; the inithooks journal shows the first-boot
scripts in about 1 s, including `15regen-sslcert`. The TLS key is
generated by both `keel-host-keys` and the older `15regen-sslcert`; that
duplication is the next candidate.

## Final stable first boot, 2026-10-28

`keel-host-keys` 1231 ms with TLS/SSH/snakeoil restored; the fence is
288 ms and passes. The TLS deduplication/ECDSA experiment was reverted:
the fence needs the cert at keel-host-keys time, and the mini server did
not start with the ECDSA pair.
